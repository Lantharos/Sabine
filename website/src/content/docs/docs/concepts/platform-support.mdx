Sabine supports three desktops: Linux on Wayland, Windows, and macOS on Apple Silicon. Every feature is built natively for each of them, and where a desktop lacks something, this page says so.

## Supported platforms

| Platform | Architectures | Requirements |
| --- | --- | --- |
| Linux | x86_64, ARM64 | A Wayland session. A GPU with Vulkan, or OpenGL where no Vulkan adapter can present. User namespaces for Chromium's sandbox. |
| Windows | x86_64, ARM64 | Windows 10 or 11 with Direct3D 12 |
| macOS | Apple Silicon | macOS 12 or later |

Not supported: X11 sessions, including XWayland-only setups; Intel Macs; mobile platforms. There is no fallback to another web engine or to windowed Chromium on any platform.

Building apps needs Rust 1.98 or newer and Bun. People who install your app need neither: the first Sabine app on a machine downloads the Sabine system and Chromium runtime, and every later app reuses them. See [Shared runtime](/docs/concepts/shared-runtime/).

### Linux desktop services

Sabine talks to the desktop through standard protocols and portals. Features whose service is missing report it in the app's diagnostics and keep the app running:

| Service | Used for |
| --- | --- |
| XDG desktop portal | File dialogs, global shortcuts, printing, appearance, opening links and folders, notifications without a notification server |
| `org.freedesktop.Notifications` | Notifications, when a notification server runs |
| StatusNotifierWatcher | The tray icon |
| A user systemd instance | The shared Chromium runtime, and starting the Sabine daemon |
| GStreamer with `playbin3` | Native video, loaded only when a page first plays one |
| `ext_background_effect_v1` | Glass blur |
| `kestrel_window_v1` | Keeping a window out of the taskbar and above others |

## Notes and gaps

### Linux

- **Wayland only.** Sabine's windows and Chromium both use Wayland. Without a Wayland session, apps don't start.
- **Glass** is a blur through `ext_background_effect_v1`. Compositors without it, such as GNOME's, show the page over a clear window. Input and opaque regions still apply.
- **Skip taskbar and always on top** have no standard Wayland protocol. Sabine asks the compositor through `kestrel_window_v1`, which Kestrel provides; elsewhere the window is placed like any other, and the window log says why.
- **The tray** needs a StatusNotifierWatcher. Desktops that don't host StatusNotifierItems themselves, such as GNOME without an extension, show no tray icon. The icon registers again whenever the watcher restarts.
- **Global shortcuts** go through the GlobalShortcuts portal. The desktop decides whether to bind them and may ask the person first; a refused shortcut is reported as `globalShortcut.failed` and the rest keep working.
- **Clipboard.** Chromium renders off screen and can't reach the compositor's clipboard, so the window host owns it: through `ext-data-control` when the compositor offers it, otherwise through the seat's data device on the window's connection. Pages get every MIME type, and the primary selection.
- **Touch keyboard.** When a field gains focus, Sabine asks the compositor to show its on-screen keyboard through the text input protocol, where the compositor supports it.
- **Window focus.** Compositors give focus only with an activation token. An app's first window carries the token its launcher handed it, and clicked notifications, shortcuts and single-instance activations pass theirs on.
- **AppArmor.** Ubuntu and similar distributions need an AppArmor profile for Chromium hosts in a user's home. See [Security model](/docs/concepts/security-model/#the-browser-sandbox).
- **Flatpak packaging** isn't a bundle target. Apps that run inside a Flatpak-style sandbox start their own Chromium through Zypak.

### Windows

- **Frameless corners** are rounded on Windows 11 and square on Windows 10.
- **Glass regions.** DWM can't blur only part of a window, so the material covers the whole window and the page's transparency decides where it shows. The input region shapes the window instead: outside it, the window neither draws nor takes clicks.
- **Out of sight.** Windows doesn't report when a window is covered, so only a minimized window counts as out of sight.
- **Input methods** get no text around the caret and can't delete around it.
- **Foreground.** A second launch of a single-instance app lets the running app take the foreground, which Windows otherwise grants only to the process the person just started.

### macOS

- **Apple Silicon only.** Bundles require a native arm64 executable.
- **Notifications** need a bundled app; macOS asks for permission the first time.
- **URL schemes and document types** must be declared in the bundle before it is signed, so test them with the bundled app rather than a development run.
- **The tray** shows only the image in the menu bar, not the title. Black-and-white icons, and icons marked as templates, follow the menu bar's appearance.
- **Tray icons and shortcuts** need the main thread's event loop. `SabineWindow::main` and `SabineProcess::wait()` run it; call `wait()` on the main thread when you manage the process yourself.
- **Inhibiting system shortcuts** needs the Accessibility permission. Without it the request is rejected and macOS offers to open its settings.
- **Glass regions** follow the blur region, minus the opaque region. Outside the input region the window ignores the mouse, switching as the pointer crosses the region's edge.
- **Input methods** get no text around the caret and can't delete around it.

### Every platform

- **Screen readers.** The off-screen browser's accessibility tree isn't exposed to UI Automation, NSAccessibility or AT-SPI. Semantic HTML still helps keyboard navigation, but Sabine windows aren't accessible to desktop screen readers.
- **Codecs.** Chromium's runtime has no H.264, HEVC or AAC decoders. Play such media through [native video](/docs/web/native-video/), which needs a transparent window.
- **Browser permissions.** Camera, microphone and geolocation requests are denied, and there is no API to grant them.
- **Pen data.** Chromium's pen input carries no tilt, twist or barrel pressure, and no button state while the pen touches the screen. Tilt and barrel buttons come through [`events.pen`](/docs/reference/javascript-api/#payloads) instead.
- **Service worker notifications** aren't supported.
